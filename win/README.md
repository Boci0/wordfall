# Wordfall for Windows - native shell (`win/`)

A frameless WinForms + WebView2 host that runs the Wordfall web game as a real Windows
desktop application. The game files are embedded in the exe and served from an in-memory
`https://wordfall.local` origin, while the page draws the entire Windows 95 chrome
(title bar, menu bar, toolbar, client, status bar) and drives the OS window through
WebView2 messages.

## Prerequisites

- Windows 10/11 x64
- [.NET 10 SDK](https://dotnet.microsoft.com/download) (build + run)
- [Microsoft Edge WebView2 Runtime](https://developer.microsoft.com/microsoft-edge/webview2/)
  (installed on most Windows 10/11 machines)
- NuGet access to nuget.org for the `Microsoft.Web.WebView2` package

The published app is **framework-dependent**: it needs the .NET 10 Desktop Runtime on
the target machine (the SDK includes it on this build machine). No .NET runtime is
bundled into the exe.

## Build

From the repo root (`wordfall/`):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File win\build.ps1
```

Build + verify the published exe in one command:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File win\build.ps1 -Smoke
```

The script:

1. regenerates `win\wordfall.ico` only if it is missing (the committed 16/32/48/256
   icon is generated by `win\make-icon.ps1` with System.Drawing; no external tools),
2. runs `dotnet publish win\Wordfall.csproj -c Release -r win-x64 --self-contained false`,
3. writes the app to `dist\Wordfall-win64\`,
4. with `-Smoke`, runs the published exe with `--smoke` and prints the JSON result.

Output folder:

```
dist\Wordfall-win64\
  Wordfall.exe                       <- double-click this
  Wordfall.dll
  Wordfall.deps.json
  Wordfall.runtimeconfig.json
  Microsoft.Web.WebView2.Core.dll
  Microsoft.Web.WebView2.WinForms.dll
  Microsoft.Web.WebView2.Wpf.dll
  WebView2Loader.dll                 <- native WebView2 loader
  runtimes\win-x64\native\WebView2Loader.dll
```

The four web files (`index.html`, `style.css`, `words.js`, `game.js`) are **embedded as
manifest resources at build time**; they are not present in the output folder. Rebuild
after the web files change.

## How it works

| File | Role |
| --- | --- |
| `Program.cs` | CLI parsing (`--smoke`, `--selftest`, `--browser-args`), single-instance mutex, console attach, selftest |
| `MainForm.cs` | borderless window, WebView2 setup, in-memory origin, title-bar messages, maximize/restore sync |
| `WebAssets.cs` | loads the four embedded files and maps request paths to bytes + Content-Type |
| `Updater.cs` | in-app updater: GitHub release check, SHA-256-verified download, staged swap + relaunch helper, version parsing |
| `UpdateProgressForm.cs` | small Win95-style download progress dialog used by the updater |
| `SmokeRunner.cs` | `--smoke` verification, JSON result file, heartbeat log, independent watchdog thread |
| `make-icon.ps1` | generates the Win95-style `wordfall.ico` (16/32/48/256) |
| `build.ps1` | one-command build/publish (and optional smoke run) |

### In-memory origin

The window shows `https://wordfall.local/index.html`. Every request is intercepted with
`CoreWebView2.AddWebResourceRequestedFilter("https://wordfall.local/*", All)` and served
from memory:

| Path | Content-Type |
| --- | --- |
| `/` or `/index.html` | `text/html; charset=utf-8` |
| `/style.css` | `text/css; charset=utf-8` |
| `/words.js`, `/game.js` | `application/javascript; charset=utf-8` |
| anything else | `404 Not Found` |

A real HTTPS origin keeps `localStorage` working (high scores) and matches how the page
behaves in a browser.

### Frameless Win95 window

- `FormBorderStyle = None`, `ShowInTaskbar = true`, client area `1200x760`, centered.
- `BackColor`/WebView2 `DefaultBackgroundColor` = `#181818`, so resizing/loading never
  flashes white.
- Maximize is constrained to the monitor working area (`MaximizedBounds`) so a
  borderless window does not cover the taskbar.
- The window icon is `win\wordfall.ico`.

### Title-bar protocol (page <-> host)

The page posts exactly these strings with `window.chrome.webview.postMessage(...)`:

| Message | Host action |
| --- | --- |
| `drag` | `ReleaseCapture()` + `SendMessage(Handle, WM_NCLBUTTONDOWN, HTCAPTION, 0)` - native window drag |
| `min` | `WindowState = FormWindowState.Minimized` |
| `max` | toggles `Normal` / `Maximized` |
| `close` | `Close()` |
| `check-update` | starts the in-app updater (Help → Check for Updates…) |

### In-app updater

The native shell checks `https://api.github.com/repos/Boci0/wordfall/releases/latest`
about 6 s after launch and on demand. A newer tag prompts Yes/No; on Yes it downloads the
win64 zip, verifies GitHub's published SHA-256 digest, extracts it under
`%LOCALAPPDATA%\Wordfall\updates\<tag>\staged`, and hands the swap to a detached PowerShell
helper (`%TEMP%\Wordfall-update-<pid>.ps1`). The helper waits for Wordfall to exit, retries
copying the staged files over the install folder, cleans up, and restarts `Wordfall.exe`.
Records/settings/profile live in `%LOCALAPPDATA%\Wordfall`, outside the install folder, so
they survive. A non-writable install folder falls back to opening the release page. The
helper accepts `-NoStart` for rehearsal against a scratch folder, and every step logs to
`%LOCALAPPDATA%\Wordfall\updates\last-update.log`.

```powershell
# updater diagnostics (no install is touched)
dist\Wordfall-win64\Wordfall.exe --check-update --current-version=1.0.0 --update-out=check.json
dist\Wordfall-win64\Wordfall.exe --update-selftest=%TEMP%\wf-update --current-version=1.0.0
dist\Wordfall-win64\Wordfall.exe --write-updater-script=%TEMP%\wf-install.ps1
```

After a max/restore toggle (and on initial page load) the host posts back a **JSON
string** so the page can update its Maximize glyph/menu item:

```js
window.chrome.webview.addEventListener('message', (e) => {
  const msg = JSON.parse(e.data); // {"type":"maximized","value":true}
});
```

The WebView2 is focused on window activation and after left clicks.

### WebView2 hygiene

Context menus, DevTools, browser accelerator keys, zoom control, status bar and built-in
error pages are disabled; popups are suppressed; the user data folder lives in
`%LOCALAPPDATA%\Wordfall\WebView2` (so `localStorage` survives restarts and the app can
run from a read-only folder).

### Startup hardening (profile in use / 0x800700AA)

A normal launch must never show the user a WebView2 error just because a profile is
locked. Startup does this:

1. A named mutex enforces one running instance. A second launch activates the existing
   window and exits silently - it never touches WebView2 and never shows a dialog.
2. `CoreWebView2Environment.CreateAsync` is tried on the configured profile.
3. If that fails (0x800700AA "resource in use", or any environment-creation COM error),
   stale Chromium `SingletonLock`/`SingletonCookie`/`SingletonSocket`/`LOCK` files are
   cleared if they can be deleted, and the same profile is retried once after ~1 s.
4. If that still fails, the app retries with a brand-new unique profile
   `%LOCALAPPDATA%\Wordfall\WebView2-<timestamp>-<rand>` (smoke mode: a unique `%TEMP%`
   folder). The saved best score starts from scratch in that rare fallback, but the app
   starts.
5. Only if all three attempts fail is the error dialog shown.

`--smoke` records the profile actually used (`userDataFolder`) and whether the fallback
was needed (`profileFallback`) in its JSON result.

Internal diagnostic (no window, no WebView2) used to prove single-instance behaviour:

```powershell
# process A: prints role=primary and holds the mutex
dist\Wordfall-win64\Wordfall.exe --instance-check --hold=4000
# process B while A runs: prints role=secondary, exits 0 silently (no dialog)
dist\Wordfall-win64\Wordfall.exe --instance-check

# force a specific (e.g. unwritable) profile location to test the fallback path
dist\Wordfall-win64\Wordfall.exe --smoke --profile-dir="C:\Program Files\WordfallTest-Profile"
```

### Diagnostics and smoke mode

```powershell
# No window, no WebView2: checks embedded resources + WebView2 runtime, writes JSON, exits 0/1
dist\Wordfall-win64\Wordfall.exe --selftest

# Full run: offscreen window, waits for the game + embedded Win95 UI, runs a seeded sim
dist\Wordfall-win64\Wordfall.exe --smoke --smoke-out="%TEMP%\smoke.json"

# Same but with a visible window (useful while debugging)
dist\Wordfall-win64\Wordfall.exe --smoke --smoke-visible

# Extra Chromium flags for constrained environments
dist\Wordfall-win64\Wordfall.exe --smoke --browser-args="--disable-gpu --no-sandbox"
```

`--smoke` writes `smoke-result.json` (next to the exe, or `--smoke-out=<path>`), a
`smoke-heartbeat.log` with startup stages, prints the JSON when a console is attached,
and exits `0` (pass) / `1` (fail). It checks:

- `window.__wordfall.version === 'M8'`,
- `document.body.classList.contains('embedded')` (the page detected WebView2),
- `#titleText` starts with `Wordfall`,
- `window.__wordfall.sim({wpm:60, mode:'skip', seed:1000})` executes and state can be read,
- the result JSON also reports `userDataFolder` (profile actually used) and
  `profileFallback` (true when the startup fallback profile was needed).

If WebView2 or the UI thread hangs, an independent watchdog thread (90 s) writes a
failure JSON and exits - the process never hangs indefinitely.

`--selftest` never creates WebView2; it verifies the four embedded resources and the
installed WebView2 runtime, prints/writes JSON, and exits 0/1.

## Known limitations / environment notes

- **Folder publish, not single-file.** Single-file publishing was tried first; the
  WebView2 host crashes on startup (`COMException 0x800700AA`, or the .NET single-file
  apphost fails to extract into `%TEMP%\.net` with error 5) because WebView2Loader must
  exist as a real file. The exe is therefore accompanied by `WebView2Loader.dll` and the
  WebView2 managed assemblies; `Wordfall.exe` itself is the double-click entry point.
- **Agent/sandboxed environments.** In the DeepSeek Harness sandbox, executables located
  inside the workspace are launched with a restricted, read-only view of the file system.
  WebView2 needs to create its profile folder, so the app cannot start when the exe is
  launched *from the workspace path* by an agent. The same published binaries run fine
  from a copy outside the workspace (e.g. `%TEMP%`); `build.ps1 -Smoke` does this
  automatically. In a normal user session (double-click), the app runs from `dist`
  normally.
- **Controlled Folder Access.** On machines with Defender CFA enabled, unsigned apps
  cannot write into `Documents` (where this repo lives), so the default
  `smoke-result.json` next to the exe may be blocked. Pass `--smoke-out=` pointing at
  `%TEMP%` (the build script does this) or allow the app in Defender.
- **Browser process crash in sandboxed launches.** Launches of the exe from the sandboxed
  workspace showed `msedgewebview2.exe` APPCRASH in `msedge.dll` (`0x80000003`), a
  Chromium CHECK caused by the inherited outer sandbox/job. It does not reproduce when
  the identical binaries are launched outside that sandbox. `--browser-args` is available
  to experiment with `--no-sandbox`, `--disable-gpu`, etc. in constrained environments.
- **No native resize borders.** The page fills the whole client area, so there are no
  drag-to-resize edges (startup size is 1200x760; Maximize fills the working area). F11 is
  not implemented - the page's own Maximize button is the supported full-screen path.
- **Keyboard shortcuts:** browser accelerators, context menus and DevTools are disabled in
  release builds; the game's keyboard handling receives normal letter/number keys.
- `Microsoft.Web.WebView2.Wpf.dll` is shipped by the NuGet package even though only the
  WinForms control is used; it is unused but harmless.
